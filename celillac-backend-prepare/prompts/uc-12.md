# UC12 — Cadastrar Produto

## 1. Identificação do caso de uso

**Código:** UC12  
**Nome:** Cadastrar Produto  
**Sistema:** CeliLac  
**Módulo:** Gerenciamento de Produtos  
**Tipo:** Caso de uso funcional

## 2. Objetivo

Permitir o cadastro de produtos na plataforma CeliLac, por meio do recebimento, da validação e da persistência das informações necessárias à criação de um novo produto.

O cadastro deverá respeitar as regras de negócio estabelecidas para o produto, impedindo o armazenamento de informações inválidas.

## 3. Atores envolvidos

**Ator principal:** Usuário autorizado a cadastrar produtos.

**Observação:** a identificação exata do ator e suas permissões precisam ser confirmadas na especificação original.

## 4. Pré-condições

Proposta de pré-condições, sujeita à confirmação:

1. O sistema CeliLac deve estar operacional.
2. O usuário deve possuir permissão para realizar o cadastro.
3. Os serviços necessários ao processamento do cadastro devem estar disponíveis.

## 5. Pós-condições

### Em caso de sucesso

1. O produto é cadastrado.
2. As informações válidas são persistidas.
3. O sistema disponibiliza uma resposta indicando o resultado da operação.

### Em caso de falha

1. O cadastro não é concluído.
2. Produtos com informações inválidas não são armazenados.
3. O sistema comunica a falha conforme o contrato da aplicação.

## 6. Fluxo principal

Fluxo proposto a partir dos componentes apresentados no material didático:

1. O ator solicita o cadastro de um novo produto.
2. O sistema recebe os dados necessários ao cadastro.
3. A aplicação verifica os dados recebidos.
4. O sistema executa as regras e validações aplicáveis.
5. O serviço de aplicação processa a solicitação.
6. O repositório realiza a persistência do produto.
7. O sistema retorna o resultado do cadastro.

## 7. Fluxos alternativos e de exceção

### FA01 — Nome obrigatório não informado

1. O sistema recebe uma solicitação de cadastro sem o nome obrigatório.
2. A validação identifica a ausência do nome.
3. O sistema rejeita o cadastro.
4. Nenhum produto inválido é armazenado.

Esse comportamento é apresentado como exemplo no material didático e precisa ser confirmado na especificação original.

### FA02 — Preço inválido

1. O sistema recebe uma solicitação contendo um preço considerado inválido.
2. A validação identifica a inconsistência.
3. O cadastro é rejeitado.
4. Nenhum produto inválido é armazenado.

**Observação:** a validação do preço é ilustrativa. O material não estabelece quais valores são permitidos ou proibidos.

### FE01 — Falha na persistência

1. O sistema tenta armazenar o produto.
2. Ocorre uma falha durante a operação.
3. A aplicação trata a falha conforme sua arquitetura e seus contratos.
4. O sistema informa que a operação não foi concluída.

Este fluxo é uma proposta técnica, não uma regra explicitamente documentada.

## 8. Regras de negócio

As seguintes regras são candidatas à confirmação:

**RN01 — Nome obrigatório:** o produto deve possuir um nome válido.

**RN02 — Validação do preço:** o preço deve atender às restrições definidas pelo domínio.

**RN03 — Integridade do cadastro:** produtos que não atendam às regras de validação não devem ser persistidos.

**RN04 — Persistência após validação:** o armazenamento deverá ocorrer somente quando as condições necessárias ao cadastro forem atendidas.

As regras acima não substituem a especificação original do UC12. Os critérios exatos de validade do nome, do preço e dos demais atributos permanecem pendentes.

## 9. Validações e restrições

O planejamento deverá considerar:

- Validação dos campos obrigatórios;
- Validação das informações recebidas;
- Validação das regras de negócio;
- Rejeição de solicitações inválidas;
- Prevenção do armazenamento de produtos inválidos;
- Tratamento das falhas do fluxo de cadastro.

As restrições específicas de formato, tamanho, valores permitidos e unicidade não estão definidas no material consultado.

## 10. Requisitos e relacionamentos relevantes

### RF01 — Cadastro de produto

O sistema deverá disponibilizar uma operação para cadastrar produtos conforme as regras estabelecidas no UC12.

### RF02 — Validação das informações

O sistema deverá verificar as informações necessárias à criação do produto.

### RF03 — Persistência

O sistema deverá permitir o armazenamento dos produtos cadastrados com sucesso.

### RF04 — Rejeição de cadastros inválidos

O sistema deverá impedir que produtos que não atendam aos critérios de validação sejam cadastrados.

### RF05 — Resposta da operação

O sistema deverá disponibilizar uma resposta compatível com o resultado do processamento.

Esses requisitos representam uma organização preliminar dos comportamentos apresentados no material e precisam ser confrontados com a especificação original.

## 11. Considerações arquiteturais

O material didático apresenta as seguintes unidades de trabalho como possibilidades para a implementação do UC12:

1. Criar a entidade `Product`.
2. Criar o DTO de cadastro de produto.
3. Implementar o serviço de aplicação responsável pelo cadastro.
4. Implementar o repositório de produtos.
5. Configurar a persistência.
6. Implementar as validações.
7. Criar o endpoint `POST /products`.
8. Implementar testes automatizados.
9. Atualizar a documentação técnica.

Essas unidades de trabalho deverão ser refinadas conforme a arquitetura efetivamente adotada no projeto CeliLac.

## 12. Critérios gerais de aceite

Os seguintes critérios são apresentados como exemplos no material de referência:

**CA01:** uma solicitação contendo dados válidos deve resultar no cadastro de um produto.

**CA02:** uma solicitação sem o nome obrigatório deve ser rejeitada.

**CA03:** uma solicitação rejeitada não deve produzir o armazenamento de um produto inválido.

**CA04:** os comportamentos especificados devem possuir testes automatizados.

Esses critérios deverão ser confirmados ou adaptados à documentação original do caso de uso.
