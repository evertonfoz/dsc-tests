# UC17 — Autenticar usuário

> **Situação:** recorte desta entrega e critérios CA01 a CA07 **aprovados** por `evertonfoz` em 2026-11-28. As pendências da seção 11 não fazem parte dessa aprovação. Fontes: o material "Criação do Projeto React e Estrutura Inicial do Frontend" (arquivo `0001-Criacao-do-Projeto-React-e-Estrutura-Inicial-do-Frontend.pdf`) e as decisões desta execução.
> **Siglas:** UC (caso de uso), API (*Application Programming Interface*, a interface pela qual outros programas usam o sistema), HTTP (*HyperText Transfer Protocol*, protocolo da web), URL (*Uniform Resource Locator*, endereço de um recurso), JWT (*JSON Web Token*, credencial assinada que identifica a pessoa), CSS (*Cascading Style Sheets*, linguagem de estilos), RF (requisito funcional), RN (regra de negócio), FA (fluxo alternativo), CA (critério de aceite), ADR (*Architecture Decision Record*, registro de decisão arquitetural).

## 1. Identificação
**Código:** UC17
**Nome:** Autenticar usuário
**Sistema:** CeliLac
**Módulo:** Frontend — autenticação
**Arquétipo:** autenticar (**esboço** do método, ainda não validado em caso real)

## 2. Objetivo
Permitir que uma pessoa entre no sistema pelo navegador e acesse a área autenticada.
**Esta entrega cobre apenas a base da interface**: telas, rotas e a URL da API. A autenticação real está adiada (`docs/adr/ADR-001-autenticacao-adiada-uc17.md`).

## 3. Atores
**Ator principal:** pessoa usuária do sistema, pelo navegador.
**Ator de apoio desta entrega:** pessoa desenvolvedora, que configura o endereço da API.

## 4. Pré-condições
1. A aplicação está em execução no ambiente local.

Para a autenticação real (adiada): a API precisaria oferecer login, o que **hoje não acontece** no `celilac-backend`.

## 5. Pós-condições
### Em caso de sucesso (desta entrega)
1. A pessoa vê a tela correspondente ao endereço acessado.

### Em caso de falha
1. Nenhuma credencial digitada é enviada a lugar algum.

## 6. Fluxo principal (desta entrega)
1. A pessoa abre o endereço raiz da aplicação.
2. O sistema redireciona para a tela de login.
3. A pessoa vê os campos de e-mail e senha e o botão "Entrar".
4. Ao enviar o formulário, o sistema **não** autentica nem envia dados à API.

## 7. Fluxos alternativos e de exceção

### FA01 — acesso direto a outra tela
1. A pessoa abre o endereço do dashboard ou o de acesso negado.
2. O sistema mostra a tela pedida, sem exigir autenticação (situação temporária, RN03).

Nenhum fluxo de exceção está definido para esta entrega (ver seção 11).

## 8. Regras de negócio
**RN01 — configuração local fora do repositório:** o arquivo `.env` não é versionado; o `.env.example` é versionado e contém a variável `VITE_API_BASE_URL`.

**RN02 — sem autenticação nesta entrega:** enviar o formulário de login não gera requisição à API.

**RN03 — rotas abertas, temporariamente:** nesta entrega, dashboard e acesso negado abrem sem autenticação. Quando a ADR-001 for retomada, esta regra deve ser substituída.

## 9. Requisitos funcionais
### RF01 — Redirecionar a raiz
O endereço `/` leva a `/login`.

### RF02 — Tela de login
`/login` mostra o título "Login", um campo de e-mail, um campo de senha e o botão "Entrar".

### RF03 — Tela de dashboard
`/dashboard` mostra o título "Dashboard" e a mensagem sobre a área autenticada.

### RF04 — Tela de acesso negado
`/unauthorized` mostra o título "Acesso negado" e a mensagem de falta de permissão.

### RF05 — Endereço da API configurável
A aplicação obtém o endereço base da API da variável `VITE_API_BASE_URL`.

### RF06 — Autenticar na API *(adiado, ADR-001)*
Enviar e-mail e senha à API e guardar o JWT recebido.

### RF07 — Proteger o dashboard *(adiado, ADR-001)*
Permitir o acesso ao dashboard somente a pessoas autenticadas.

### RF08 — Controlar por perfil *(adiado, ADR-001)*
Levar à tela de acesso negado a pessoa autenticada sem o perfil necessário.

## 10. Critérios de aceite
**CA01:** dado o endereço `/`, quando a pessoa o abre, então o endereço passa a ser `/login` e a tela de login aparece.

**CA02:** dado `/login`, então aparecem o título "Login", um campo do tipo e-mail, um campo do tipo senha e o botão "Entrar".

**CA03:** dado `/dashboard`, então aparecem o título "Dashboard" e o texto sobre a área autenticada.

**CA04:** dado `/unauthorized`, então aparecem o título "Acesso negado" e o texto de falta de permissão.

**CA05:** dado um valor em `VITE_API_BASE_URL`, então a aplicação expõe esse mesmo valor como endereço base da API.

**CA06:** o Git ignora o `.env`, e o `.env.example` é versionado com `VITE_API_BASE_URL`.

**CA07:** dado o formulário de login preenchido, quando é enviado, então nenhuma requisição é feita à API.

## 11. O que ainda não está definido
Nada abaixo é requisito. Quem decide é a pessoa responsável pelo caso de uso.

- **P1 — endereço inexistente** (ex.: `/abc`): o material não diz o que mostrar. Em 2026-11-28, `evertonfoz` decidiu **deixar em aberto** nesta entrega (a página fica em branco).
- **P2 — variável `VITE_API_BASE_URL` ausente:** o material não diz como a aplicação reage. Em 2026-11-28, `evertonfoz` decidiu **deixar em aberto**; rever junto com o login, quando a variável passar a ser usada.
- **P3 — recarga no envio do formulário:** sem tratamento, o navegador recarrega a página ao enviar. O material não diz se isso é aceitável. Em 2026-11-28, `evertonfoz` decidiu **deixar em aberto**; tratar junto com o login, antes de dar o atributo `name` aos campos (senão a senha apareceria no endereço).
- **P4 — regras de credenciais, mensagens de erro e expiração do token:** serão definidas quando a ADR-001 for retomada.
